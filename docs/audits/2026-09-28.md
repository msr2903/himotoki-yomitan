# Code audit — 28 September 2026

Reviewed the fork's Himotoki save path, account lifecycle, popup controls, dictionary identity mapping, cloud serialization, and test/build setup. Also sampled the inherited translator, language transformer, LRU cache, Anki connection, and audio downloader. This is a targeted source audit, not an exhaustive security assessment or a browser performance profile.

The patch is based on `origin/master` at `a71cb37f`. Work in progress on `feature/himotoki-theme` was left untouched in the original worktree.

## Performance evidence

A deterministic test launches 20 concurrent `getSaved(false)` calls against a cold cache. The original implementation makes 20 document requests; the patch makes one. This is a 95% request reduction for that workload, including avoiding repeated JSON decoding. Warm-cache calls still make no requests, and explicit refresh still fetches fresh data. A separate mixed read/save test checks that concurrent callers share one token refresh.

This measures request counts with mocked network responses, not real browser latency. No claim is made about overall lookup speed or frame rate. Saves still read and write the full favorites array, so cost grows with library size.

## Remaining code weaknesses

1. **Popup save state and duplicate submissions (medium).** In [DisplayHimotoki](../../ext/js/display/display-himotoki.js), `_onHotkeySave` bypasses the disabled button, `_save` has no pending-save guard, and `_updateSavedState` can reset a button while it is saving. Rapid hotkeys can start competing writes and exhaust conflict retries. Add a per-entry pending operation shared by click and hotkey paths, honor the integration's enable setting, and test lookup changes during saves. The saved-state update also builds full favorite payloads, traversing glossaries just to compare identities; extracting a cheap identity helper would reduce popup work.
2. **Unbounded network waits (medium).** `_fetchGoogleApi` has no timeout. A stalled request can leave save controls waiting indefinitely; shared reads now share that wait. Add cancellation/timeouts with visible retry controls. Automatic retries should distinguish reads from writes whose outcome is uncertain.
3. **Runtime schema validation (medium).** [toSavedBlob](../../ext/js/data/himotoki-saved-blob.js) casts array elements without validation, while consumers destructure them as valid favorites/folders. A null or malformed entry can break listing and saving. Validate responses and stored sessions, preserve unknown data, and refuse unsafe writes to unsupported schema versions. The patch preserves unknown top-level fields, but does not make arbitrary future fields inside the favorites array lossless.
4. **OAuth callback hardening (review needed).** `_getGoogleIdToken` generates a nonce but does not check it, and does not send/validate a state parameter. Review the complete callback contract and add transaction binding plus browser-level sign-in tests. Source inspection alone does not establish an exploitable account takeover; the identity API and Firebase perform additional checks outside this repository.
5. **Audio search escaping (medium).** [AudioDownloader](../../ext/js/media/audio-downloader.js) inserts terms and contributor names directly into regular expressions and query URLs for Wikimedia audio. Regex characters can change matching or throw, and URL delimiters can change the query. Escape regex literals and construct query parameters through `URLSearchParams`; cover terms such as `C++`, parentheses, and ampersands.
6. **Integration coverage (medium).** Existing browser integration tests cover clipboard search and Anki, but not Himotoki sign-in, save, fallback, account switching, or service-worker restart. The new mocked tests cover concurrency without proving compatibility with deployed Firestore rules or real browser identity flows.

The dictionary-name heuristic remains a compatibility assumption. An explicit dictionary identity setting or import metadata would support renamed/custom JMdict-compatible packs more reliably. The patch prevents future collisions; it does not attempt to repair previously misidentified saved words.

## Suggested product improvements

1. **Reliable save feedback.** Show pending/saved/failed status consistently, an explicit retry, and a link to the saved word. Make status accessible to screen readers and keep hotkeys consistent with button state.
2. **Offline save queue.** Persist pending saves with their originating account and stable word identity. Show a pending count, retry with backoff when online, and prevent a later account from receiving earlier queued saves. This requires explicit handling of the uncertain outcome of interrupted writes.
3. **Mining preview and folder picker.** Let readers adjust the definition, sentence, and destination folder before saving without opening settings. Add a separate page-title privacy toggle; currently the title is included independently of the sentence/URL options.
4. **Larger, scalable libraries.** The current model has a 500-word cap and rewrites the favorites array for every save. Explore per-word records and incremental synchronization with the website, backed by a migration and matching server rules.
5. **Connection diagnostics and onboarding.** A compact setup flow could confirm dictionary import, account state, folder access, and one test save. Show actionable connection errors without exposing tokens or page contents.
6. **A repeatable performance budget.** Track cold/warm lookup latency, popup rendering with a large structured dictionary, saved-library request counts, and bulk-import memory. Use these measurements to prioritize further optimizations instead of changing the established translator speculatively.

## Validation and limits

The new tests first reproduced 10 failures in the original implementation. The final regression suite additionally covers account switching during reads, stale refresh failures, cancellation of pending sign-in, storage retry, invalid-session responses, rate limiting, write conflicts, and new-document creation.

Validation passed: JavaScript lint (one existing warning in `anki-note-builder.js`), all four TypeScript projects, CSS/HTML checks, 4,872 unit tests (46 skipped), 24 options tests, 135 JSON tests, Markdown formatting, and the all-target build dry run. The patch adds 22 tests (20 client tests and two dictionary identity regressions). Generated libraries must first be prepared with `npm run build:libs` in a fresh checkout. Real Google sign-in, deployed Firestore rules, and browser end-to-end flows were not exercised, and no live saved-word data was changed.
